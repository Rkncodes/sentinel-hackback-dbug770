# API — Sentinel

**Card:** SENTINEL — Intrusion Detection & Auto-ban · **Original:** CrowdSec

This is the HTTP contract of **our rebuild**, for the core and the two improvements in [PRD.md](PRD.md). It is a specification; nothing is implemented. Data shapes follow [DATA_MODEL.md](DATA_MODEL.md).

It is not CrowdSec's API. CrowdSec's bouncer-facing endpoints are `GET /v1/decisions` and `GET /v1/decisions/stream` (O-4, O-16 in [OBSERVATIONS.md](OBSERVATIONS.md)); Sentinel shares neither their paths nor their shapes.

## 1. Endpoints at a glance

| # | Method | Endpoint | Key | Purpose |
|---|---|---|---|---|
| 1 | `POST` | `/v1/login-attempts` | Portal key | Report the outcome of one login attempt |
| 2 | `GET` | `/v1/check` | Portal key | Ask whether a request from an IP may proceed right now |
| 3 | `GET` | `/v1/bans` | Admin key | View recent bans, with the reason for each |
| 4 | `DELETE` | `/v1/bans/{id}` | Admin key | Lift a ban early |

There are four endpoints because there are four things a caller needs to do. Endpoints 1 and 2 are enough for the three Killer Tests. Endpoints 3 and 4 serve the audit and manual-unban requirements (FR-9, FR-10). Neither improvement adds an endpoint: Improvement 1 is a parameter of endpoint 2, and Improvement 2 is a field in the answers of endpoints 1 and 2.

One extension was added after this contract was finalized: the **success alert**, a `warning` field in the answer of endpoint 1 (see "The Warning object"). It adds no endpoint and changes no existing field.

## 2. Conventions

- **Format.** Request and response bodies are JSON (`Content-Type: application/json`).
- **Authentication.** Every request carries `Authorization: Bearer <key>`. There are two keys:
  - the **portal key**, accepted only by endpoints 1 and 2;
  - the **admin key**, accepted only by endpoints 3 and 4.
- **Timestamps.** UTC, RFC 3339, millisecond precision, for example `2026-10-05T10:00:00.000Z`. Every timestamp is generated by Sentinel from its own clock. Callers never send one; a timestamp in a request is ignored.
- **Test clock.** In tests Sentinel's clock is replaced by a controllable one, so time-dependent behavior can be checked exactly. This is done inside the test harness, not through a public endpoint.
- **IP addresses.** IPv4 or IPv6 text. Responses return the address in Sentinel's canonical form.
- **Expiry rule.** A ban that has not been lifted by hand is **active iff now < `expires_at`** and **expired iff now ≥ `expires_at`**. Every endpoint uses this one rule.

### Errors

Every error uses the same body:

```json
{ "error": { "code": "invalid_ip", "message": "ip is not a valid IP address" } }
```

| Status | `code` | When |
|---|---|---|
| 400 | `invalid_request` | Body or query is malformed, a required field is missing, or a value is not one of those allowed |
| 400 | `invalid_ip` | `ip` is not a single valid IP address |
| 401 | `unauthorized` | Key missing or wrong |
| 403 | `forbidden` | Key is valid but not accepted by this endpoint |
| 404 | `not_found` | No ban with that `id` |

### The Ban object

```json
{
  "id": "ban_01HZX3",
  "ip": "203.0.113.7",
  "reason": "failed_login_threshold",
  "status": "active",
  "triggered_at": "2026-10-05T10:00:41.250Z",
  "expires_at": "2026-10-05T10:15:41.250Z",
  "revoked_at": null,
  "rule": { "threshold": 10, "window_seconds": 60, "ban_duration_seconds": 900 },
  "evidence": [
    { "received_at": "2026-10-05T10:00:02.100Z", "username": "jdoe" }
  ]
}
```

- `status` is `active`, `expired` or `revoked`, computed at the time of the response.
- `evidence` lists the failures that caused the ban (shortened above; a real one has `threshold` entries). It is returned only to the admin key. Answers to the portal key never include it.
- `username` is `null` where the portal did not send one.

### The Explanation object

Improvement 2. Returned to the portal with every answer that says an IP is banned, for display to the blocked person.

```json
{
  "blocked": true,
  "reason_code": "failed_login_threshold",
  "message": "Sign-in from your network address is temporarily blocked because of too many failed sign-in attempts.",
  "started_at": "2026-10-05T10:00:41.250Z",
  "expires_at": "2026-10-05T10:15:41.250Z",
  "retry_after_seconds": 852
}
```

- `started_at` and `expires_at` equal the ban's `triggered_at` and `expires_at`.
- `retry_after_seconds` is the time remaining, rounded up to a whole second.
- It never contains evidence, usernames or rule values.
- It is `null` whenever the IP is not banned.

### The Warning object

Extension. Returned to the portal in the answer to a `success` report when that success followed repeated failed attempts for the same account from the same address: the password may have been guessed.

```json
{
  "code": "success_after_failed_attempts",
  "message": "Successful login followed repeated failed attempts from this address.",
  "failed_attempts": 5
}
```

- `failed_attempts` is the number of failures inside the window for the reported `ip` and `username`.
- It contains no username, no timestamps and no evidence.
- It is advisory. Sentinel bans nothing because of it; what to do (for example ask for re-verification, or notify the account owner) is the portal's decision.
- The `warning` field is present only when the alert fires. It is absent otherwise.

## 3. Endpoints

### 3.1 `POST /v1/login-attempts`

Report that a login attempt happened. The portal calls this after it has verified the credentials.

**Request body**

| Field | Type | Required | Notes |
|---|---|---|---|
| `ip` | string | Yes | Client IP of the attempt |
| `outcome` | string | Yes | `"success"` or `"failure"` |
| `username` | string | No | Account name tried |

```json
{ "ip": "203.0.113.7", "outcome": "failure", "username": "jdoe" }
```

**Response `200`**

| Field | Type | Notes |
|---|---|---|
| `ip` | string | Canonical form |
| `banned` | boolean | Whether the IP is banned after this report was processed |
| `ban_triggered` | boolean | `true` only if this report created the ban |
| `ban` | Ban object or `null` | The active ban, without `evidence`; `null` when not banned |
| `explanation` | Explanation object or `null` | Present when `banned` is `true` |
| `warning` | Warning object | Extension. Present only when the success alert fires; absent otherwise |

```json
{
  "ip": "203.0.113.7",
  "banned": true,
  "ban_triggered": true,
  "ban": {
    "id": "ban_01HZX3",
    "ip": "203.0.113.7",
    "reason": "failed_login_threshold",
    "status": "active",
    "triggered_at": "2026-10-05T10:00:41.250Z",
    "expires_at": "2026-10-05T10:15:41.250Z",
    "revoked_at": null,
    "rule": { "threshold": 10, "window_seconds": 60, "ban_duration_seconds": 900 }
  },
  "explanation": {
    "blocked": true,
    "reason_code": "failed_login_threshold",
    "message": "Sign-in from your network address is temporarily blocked because of too many failed sign-in attempts.",
    "started_at": "2026-10-05T10:00:41.250Z",
    "expires_at": "2026-10-05T10:15:41.250Z",
    "retry_after_seconds": 900
  }
}
```

**Behavior**

- A `failure` from an IP that is not banned is counted. A failure counts toward the threshold if it was received no more than 60 seconds before the current one. If this is the 10th such failure, the ban exists before this response is sent.
- A `success` is never counted and never resets the count.
- **Success alert (extension).** A `success` that carries a `username`, from an IP that is not banned, is answered with a `warning` if at least 5 failures (configurable) for the same `ip` and `username` were received no more than 60 seconds before it. Failures for other usernames or other IPs do not contribute, and a report without a `username` never produces the alert. The alert changes nothing: no ban is created or modified and the failure count is neither increased nor reset.
- A report from an IP that is already banned is not counted, whatever its outcome. It does not extend the ban or create another. The response has `banned: true` and `ban_triggered: false`.
- **If the response has `banned: true`, the portal must not create a session**, even when the reported outcome was `success`.
- Reports for the same IP are processed atomically, one after another. Concurrent reports cannot create two bans or lose a failure.

**Errors:** `invalid_request`, `invalid_ip`, `unauthorized`, `forbidden`.

### 3.2 `GET /v1/check`

Ask whether a request from an IP may proceed at this moment. It changes nothing.

**Query parameters**

| Parameter | Required | Notes |
|---|---|---|
| `ip` | Yes | The address to check |
| `context` | No | `login` (default) for a new login attempt; `session` for a request the portal has already identified as belonging to a valid authenticated session |

Examples:
- `GET /v1/check?ip=203.0.113.7`
- `GET /v1/check?ip=203.0.113.7&context=session`

**Response `200`**

| Field | Type | Notes |
|---|---|---|
| `ip` | string | Canonical form |
| `context` | string | The context the answer applies to |
| `banned` | boolean | `true` exactly when the IP has an active ban. Not affected by `context` |
| `allow` | boolean | Whether the portal should let the request proceed |
| `ban` | Ban object or `null` | The active ban, without `evidence`; `null` when not banned |
| `explanation` | Explanation object or `null` | Present when `banned` is `true` |
| `checked_at` | timestamp | The instant the answer is true for |

How `allow` is decided:

| `context` | IP not banned | IP banned |
|---|---|---|
| `login` | `allow: true` | `allow: false` |
| `session` | `allow: true` | `allow: true` |

Not banned:

```json
{
  "ip": "198.51.100.20", "context": "login",
  "banned": false, "allow": true,
  "ban": null, "explanation": null,
  "checked_at": "2026-10-05T10:01:00.000Z"
}
```

Banned, existing session (Improvement 1):

```json
{
  "ip": "203.0.113.7", "context": "session",
  "banned": true, "allow": true,
  "ban": { "id": "ban_01HZX3", "status": "active", "...": "Ban object without evidence" },
  "explanation": { "blocked": true, "...": "Explanation object" },
  "checked_at": "2026-10-05T10:01:00.000Z"
}
```

**Behavior**

- `banned` is computed from `expires_at` and `checked_at` by the expiry rule: banned iff `checked_at` < `expires_at` for a ban that has not been lifted.
- An omitted `context` is treated as `login`, the stricter case. Any other value is `invalid_request`.
- A `session` check never changes the ban. It does not remove, shorten or weaken it, and is never counted. `banned` stays `true` and `expires_at` stays the same.
- Sentinel does not verify sessions. By sending `context=session` the portal asserts that it has validated the session itself.
- An IP that has never been seen is simply not banned. That is not an error.

**Errors:** `invalid_request`, `invalid_ip`, `unauthorized`, `forbidden`.

### 3.3 `GET /v1/bans`

A bounded audit view for administrators: the most recent bans that match the filters.

**Query parameters**

| Parameter | Required | Notes |
|---|---|---|
| `ip` | No | Only bans for this address |
| `status` | No | `active`, `expired` or `revoked`. Omitted means all |
| `limit` | No | Maximum number returned. Default 50, maximum 200 |

Example: `GET /v1/bans?status=active`

**Response `200`**

```json
{
  "bans": [
    { "id": "ban_01HZX3", "ip": "203.0.113.7", "status": "active", "...": "full Ban object including evidence" }
  ]
}
```

- Bans are ordered by `triggered_at`, newest first.
- Each entry is a full Ban object, including `evidence`.
- No match returns `{ "bans": [] }`.
- **There is no pagination.** The view returns at most `limit` bans, 200 at most, and older matches are not reachable through it. To look further back, narrow the request with `ip` or `status`. This is a deliberate limit for the hackathon scope.

**Errors:** `invalid_request`, `invalid_ip`, `unauthorized`, `forbidden`.

### 3.4 `DELETE /v1/bans/{id}`

Lift a ban before it expires. The record is kept; only `revoked_at` is set.

**Path parameter:** `id`, the ban's identifier.

**Response `200`:** the full Ban object after the request.

**Behavior**

- If the ban is `active`, `revoked_at` is set to now and the status becomes `revoked`. From that moment `GET /v1/check` reports the IP as not banned.
- The IP's failure count is cleared at the same time. New failures can ban it again, starting from zero.
- **The request is idempotent.** If the ban is already `revoked` or `expired`, nothing changes: `revoked_at` is not altered, no failure count is touched, and the current Ban object is returned with `200`. Sending the request any number of times has the same result as sending it once.

**Errors:** `not_found`, `unauthorized`, `forbidden`.

## 4. The Killer Tests in API terms

| Test | Calls | Expected |
|---|---|---|
| KT-1: 10 failed logins from one IP within one minute → that IP is banned. | 10 × `POST /v1/login-attempts` with `failure` for IP *A*, all within 60 s; then `GET /v1/check?ip=A` | Reports 1 to 9: `banned: false`. Report 10: `banned: true`, `ban_triggered: true`. Check: `banned: true`, `allow: false` |
| KT-2: A normal user logging in at the same time is not affected. | During KT-1: `POST /v1/login-attempts` with `success` for IP *B*; `GET /v1/check?ip=B` before, during and after | Always `banned: false`, `allow: true`, `ban: null` |
| KT-3: The ban is lifted exactly when it expires. | `GET /v1/check?ip=A` one instant before `expires_at`, then at `expires_at` | First: `banned: true`. Second: `banned: false`, `allow: true` |

KT-3 uses the test clock described in section 2.

The improvements in API terms:

| Check | Calls | Expected |
|---|---|---|
| Improvement 1 | While *A* is banned: `GET /v1/check?ip=A&context=session`, then `GET /v1/check?ip=A` | First: `banned: true`, `allow: true`. Second: `banned: true`, `allow: false`, same `expires_at` |
| Improvement 1, no bypass | While *A* is banned: `POST /v1/login-attempts` with `success` for *A* | `banned: true`, `ban_triggered: false` |
| Improvement 2 | Any answer above with `banned: true`; any with `banned: false` | `explanation` present with `started_at` and `expires_at`; `explanation: null` |

## 5. When Sentinel does not answer

This is the portal's side of the contract (P-3 and P-4 in [PRD.md](PRD.md)).

| The portal was handling | Sentinel times out or returns a server error | Portal behavior |
|---|---|---|
| A login attempt (check or report) | No usable answer | Refuse the attempt with a temporary "try again shortly" error. Do not create a session |
| A request in an existing session | No usable answer | Let the request continue |

## 6. Deliberately absent

| Not provided | Reason |
|---|---|
| An endpoint to create a ban by hand | Not required by the card or the Killer Tests |
| A stream or webhook of ban changes | The portal asks at the moment it needs the answer, so nothing has to be pushed |
| Endpoints to change Config | Config is read at start-up |
| Session endpoints | The portal owns sessions; Sentinel stores none |
| Pagination on `GET /v1/bans` | It is a bounded view; see 3.3 |
